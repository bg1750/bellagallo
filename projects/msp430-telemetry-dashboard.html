MSP430 Telemetry Dashboard

A complete hardware-to-browser telemetry system for an ultra-low-power sensor node: C firmware on an MSP430FR6989 streams live temperature and supply-voltage readings, a Python service validates and stores them, and a web dashboard renders them end-to-end — live hardware data only, no simulation.

C (MSP430) Python FastAPI WebSocket SQLite JavaScript Canvas API HTML5 CSS3
GitHub

The Problem

Sensor data on an embedded device usually stops at a serial console — readable in the moment, but not something you can actually watch, chart, or act on. I wanted the full path: an ultra-low-power microcontroller sampling real sensors, and that data arriving in a browser as a live, operator-style dashboard — robust enough that a flaky cable or a corrupt byte never takes the whole pipeline down.

What It Does

C firmware on an MSP430FR6989 reads the internal temperature sensor and the chip's own supply voltage through the ADC, shows the rounded temperature on the on-board segment LCD, and streams framed TEMP and VOLT readings over UART while an LED blinks as a heartbeat. It's register-level and deliberately minimal — a plain polled loop on the internal oscillator, no crystal or RTOS — so bring-up stays deterministic. A Python host uses pyserial to read those frames, validates each XOR checksum, timestamps and stores them in SQLite, and broadcasts them over a FastAPI WebSocket. The dashboard subscribes to that live stream and renders it with a hand-rolled, high-DPI Canvas strip chart — no charting library — plus stat tiles, an alarm state machine (nominal / near-limit / high / low), and an event log that records only true state transitions.

Safety-Critical Mindset

Handling the ugly cases is the point. The host validates every frame and silently drops anything corrupt or partial — counted, never fatal — so unplugging the board mid-stream or injecting a bad byte never crashes the pipeline, and the firmware's hot path is bounded so a stalled peripheral can't hang it. On the dashboard, crossing a low or high threshold flips the status tile to an alarm and the log captures the transition and recovery. The logic that matters most is locked down with tests: the alarm state machine (including exact-threshold behaviour) and the Python frame parser, with unit, end-to-end, and accessibility checks running in CI.

Vision

Next steps are pushing calibration settings from the dashboard back down to the device, wiring up an external light sensor (the protocol already carries the tag), and replaying chart history straight from the host's SQLite store.
